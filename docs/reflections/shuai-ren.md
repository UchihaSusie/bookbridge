# Individual Reflection Shuai Ren

The biggest lesson I learned from this project is that good design does not come all at once. It comes from trying things, finding problems, and then improving. When we first started BookBridge, my idea was simple. We would just take the whole PDF and translate everything from start to finish. But very quickly I realized this does not work well. The translated paragraphs had no connection to each other. Names and important words kept changing between chapters, and the result felt broken and hard to read.

So we tried adding a glossary. The glossary would store key terms and their translations so the AI could stay consistent. This was a good idea in theory, but in practice it created a new problem. Every time we translated a chapter, we had to scan through the entire glossary, and that used a lot of tokens. For a long book with hundreds of terms, this became expensive and slow. I learned that solving one problem can easily create another if you do not think carefully about the cost.

After that, I came up with a different approach. Instead of translating everything or loading the full glossary, we would break the book into chapters and only translate one chapter at a time. After finishing each chapter, we would save a short summary of about one hundred words that captured the key context. Then when translating the next chapter, we would include that small summary instead of the whole glossary. This way the AI still understood the story so far, but we did not waste tokens on information that was not needed. However, we later found even this was not perfect because sometimes the summary missed important details.

The design that worked best in the end was to let the user decide. We scan the PDF and generate a table of contents from the original text. The user can browse the chapters, pick the one they want, and confirm the translation. Only then do we spend tokens on that chapter. After each translation, we update the glossary and the context summary so future chapters stay consistent. This gave users control over what they paid for and made the whole process feel much more efficient. Looking back, this iterative design process was the most valuable thing I experienced. Each version taught me something the previous one could not.

One thing that worked better than expected was the TDD skill we built for Claude Code. The first version was basic, but after we iterated it to version two with proper pre-flight checks and dependency verification, it saved us a lot of time. Claude would follow the red, green, refactor cycle reliably, and the code quality improved because of it.

One thing that did not work well was that I did not use sub-agents early enough. During Sprint 1, I was doing most of the code review myself instead of letting the code reviewer agent handle it. If I could do this project again, I would set up the sub-agents and hooks from the very beginning so the quality checks run automatically from day one. I would also spend more time planning the translation pipeline design on paper before writing any code, because most of the wasted effort came from rebuilding things I had not thought through carefully enough.
